# AJIO Visibility Data Pipeline

A local-first, hourly keyword-visibility pipeline. For each of 50 keywords it records every product unit a shopper would see (organic, sponsored product, sponsored brand banner), with ranks, prices and deals, and it monitors itself: completeness per keyword per hour, email alerts, and recovery.

> **Data source: MOCK ONLY.** AJIO's robots.txt disallows `/search` and `/api/*`, so this project makes **no automated requests to AJIO**. Every product, price, rating, campaign and placement in the database is synthetic, generated by a seeded generator or taken from labelled fixtures. The live adapter fails closed. See [`docs/source_research.md`](docs/source_research.md).

## Quick start (about 3 minutes, no credentials)

Requires Python 3.10+.

```powershell
# Windows PowerShell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
Copy-Item .env.example .env
pytest -q                          # full suite, includes every curveball test
python -m src.main --run-once      # one collection of all 50 keywords
python -m src.main --demo          # missing slot -> alert -> late backfill -> recovery email
python -m streamlit run src/dashboard/app.py
```

```bash
# macOS / Linux / WSL
python3 -m venv .venv && source .venv/bin/activate
python -m pip install --upgrade pip && pip install -r requirements.txt
cp .env.example .env
pytest -q && python -m src.main --run-once && python -m src.main --demo
python -m streamlit run src/dashboard/app.py
```

A run takes about one second with the mock. Against a real site the configured politeness limit (below) would make it roughly 3.5 minutes.

## Commands

| Goal | Command |
|---|---|
| Collect all keywords for the current IST hour | `python -m src.main --run-once` |
| Collect one keyword only (diagnostics) | `python -m src.main --run-once --keyword "men white sneakers"` |
| **Backfill a specific past hour** | `python -m src.main --run-once --hour 2026-10-16T09:00:00+05:30` (09:00 IST slot; recorded as trigger `backfill`) |
| Backfill the last N completed hours | `python -m src.main --backfill-hours 3` |
| **Hourly scheduling** (foreground) | `python -m src.main --schedule` |
| Hourly scheduling with cron / Task Scheduler | see [`config/cron.example`](config/cron.example) |
| Check an hour: missing slots, triggers, alert/recovery | `python -m src.main --check-completeness --hour 2026-10-16T09:00:00+05:30` |
| **Recover from a database failure** (no refetch) | `python -m src.main --reload-raw --hour 2026-10-16T09:00:00+05:30` |
| Full missing-slot story for the evidence pack | `python -m src.main --demo` |
| Dashboard | `python -m streamlit run src/dashboard/app.py` |

`--hour` accepts any ISO 8601 time (with or without an offset) and is floored to the top of its **IST hour** (slots are IST hours, stored as UTC instants: 10:00 IST = `2026-10-16T04:30:00Z`). **`scheduled_hour` is the slot a row belongs to; `time_stamp` is when the page was actually fetched.** A run that starts at 10:59:58 IST and finishes at 11:00:40 IST still writes the 10:00 IST slot (see I-8 in `DECISIONS.md`).

## Configure targets

`config/targets.json` holds the 50 keywords (broad and specific, plus two nonsense keywords expected to return nothing). `config/settings.yaml` holds the adapter, pages per keyword (`max_pages: 2`), timeouts, retry/backoff/jitter, rate limit, grace period, completeness threshold and alert settings. Nothing is hard-coded in the source; secrets only come from `.env`.

## How hourly scheduling works

`--schedule` uses APScheduler: a cron job at the top of every IST hour (minute 30 of the UTC clock) (`max_instances=1`, `coalesce=True`) that (1) runs all targets for that hour, then (2) checks the previous hour (its grace period has now passed) and the current hour. Cron or Task Scheduler can call the same one-shot commands instead. Either way a run is **idempotent per hour** and **protected against overlap** by a database lock: a second run that fires while the first is still working is recorded as `skipped_overlap` and fetches nothing; its slot then shows as missing until it is backfilled.

## What the pipeline does

```
targets + settings -> run + lock -> fetch (retry, backoff+jitter, rate limit) -> RAW snapshot on disk (+ sidecar)
  -> parse -> validate + dedupe -> ranks -> SILVER rows (upsert) -> target_hour_status -> completeness + triggers
  -> alert_incident -> email (file sink or SMTP)  ->  dashboard (reads the same SQLite tables)
```

## Where data lives

| What | Where |
|---|---|
| Tables (run ledger, targets, silver rows, statuses, incidents, lock) | `data/pipeline.db` (SQLite; DDL in `sql/schema.sql`) |
| Raw evidence (Bronze) | `data/raw/platform=AJIO/date=YYYY-MM-DD/hour=HH/<run_id>/<keyword>__p<page>.html` plus `.meta.json` |
| Alert emails (file sink) | `data/outbox/*.eml` |
| Sample payloads for reviewers | `samples/raw_payloads/` |

`data/` is git-ignored: it is generated by running the project.

## Status vocabulary

Per target-hour: `success`, `zero_result` (explicit no-results page; counts as complete), `partial`, `parse_failed`, `blocked`, `failed`, `running`, `missing` (no terminal status after the grace period), `not_yet_due`. Per run: `running`, `success`, `partial`, `failed`, `skipped_overlap`. Status is derived from what the parser and database actually saw, never from a process exit code.

## Alerts and email

Seven triggers: run failed after retries, slots missing after the grace period, completeness below threshold, parser/schema errors, row-count drop against a rolling baseline, stale data, blocked target. One incident exists per platform-hour; all active triggers go into **one** email (40 failed targets means one message). It resends only when the set of triggers changes or after the cooldown, and exactly one `[RECOVERED]` email is sent when the hour is healthy again. Email contains platform, hour (UTC and IST), run_id, affected targets, expected vs observed, reason, first-detected time, dashboard link and a next step.

**Trigger a missing-slot alert:** `python -m src.main --check-completeness --hour <any past hour that was never run>`, or just run `--demo`.

**Configure email safely:** copy `.env.example` to `.env` (git-ignored) and set values there; never commit credentials.

* `ALERT_SINK=file` (default): emails are written to `data/outbox/` and need no server.
* `ALERT_SINK=smtp`: send through `SMTP_HOST`/`SMTP_PORT`. For a local catcher run Mailpit (`docker run -p 8025:8025 -p 1025:1025 axllent/mailpit`), keep `SMTP_HOST=localhost`, `SMTP_PORT=1025`, and open http://localhost:8025. `SMTP_USER`/`SMTP_PASSWORD`/`SMTP_STARTTLS` are read from the environment only. An SMTP failure is logged; the incident stays open and delivery is retried at the next check, so monitoring state is never lost.

## Recovering from a failure

* **A slot is missing or failed:** fix the cause, then backfill the hour. The incident resolves and one recovery email is sent at the next check.
* **The database was down during loading:** raw files are already on disk. Once the database is back run `--reload-raw --hour <hour>`; it re-parses the stored files and loads them without any fetching, preserving the original `time_stamp` values. Running it twice creates no duplicates.
* **A run crashed:** its `running` slots turn `missing` after the grace period; the lock is released automatically once the run is marked finished, or after 4 hours.

## Mocked vs live

| | Status |
|---|---|
| Source pages | **Mock**: seeded generator (`src/collectors/synthetic.py`) and labelled HTML fixtures in `tests/fixtures/` |
| Live AJIO collection | **Disabled** (robots.txt disallows search and API paths); `AjioAdapter` raises `PermissionError` |
| Parser contract | Built for the mock structure, **not** AJIO's live DOM |
| Everything else (storage, scheduling, lock, retries, completeness, alerts, dashboard, reload) | Real, runs locally, covered by tests |

Politeness settings that a live adapter would use: 1 request per 2 s (0.5 rps), exponential backoff with jitter, `Retry-After` honoured within a 10 s budget. 50 keywords x 2 pages = 100 requests, about 200 s plus response time, well inside the hour.

## Tests

```bash
pytest -q
```

80 tests: parser on fixtures (including the JSON-LD layer), ranks, pagination, upsert/idempotency, empty results, timeout/retry/jitter, rate limiting, malformed payloads, missing slots, every alert trigger, email content, dedupe/cooldown/recovery, SMTP behaviour, raw layout, running/missing states, and one or more tests per curveball. Assertions use exact values (ranks, statuses, row counts, subjects). See [`KNOWN_GAPS.md`](KNOWN_GAPS.md) for what is not covered.
